# 실제 서버 main API 연결 — 2026-11-03

## 연결 기준

- GitHub `origin/main`을 fetch해 `3c6310e`까지 확인했다. 직전 통합 기준 `0cd7589` 이후 변경은 런처 아이콘 PR #16이며, 이번에 사용하는 API 규격은 동일하다. 최신 main 전체를 다시 merge하거나 서버를 배포한 작업은 아니다.
- 설치 앱의 `SERVER_BASE_URL`은 `http://158.101.141.165/`이다. PC 로컬 서버나 adb reverse가 필요하지 않다.
- 기존 냉장고 아이콘·배경색·추가순/가나다순/분류순·삭제·기본 재료 체크·직접 입력 자동완성·식재료 추천을 유지했다. 일반 앱 대신 `.cloudtest` 앱을 `adb install -r`로 설치했으며 데이터 초기화는 하지 않았다.
- 서버 코드·배포 설정은 이번 변경에서 수정하지 않았다. GitHub 업로드·PR 생성·배포·SSH 접속도 하지 않았다.

## 사용자 흐름과 API

1. **목록 조회:** `POST /recipes/recommend`, `ingredients`에 냉장고의 이름 목록을 전송한다. 일반 추천은 AI를 호출하지 않는다. 부족한 재료는 이 응답을 우선 사용한다. 서버는 일부 기본 조미료의 보유를 가정하며 수량을 확인하지 않는다.
2. **명시적 AI 요청:** 목록의 **AI 레시피 제안 받기** → `POST /recipes/recommendations`, `ingredient_ids`와 `revision_limit: 1`을 전송한다. 수정할 레시피는 서버가 고른다. 서버 내부 재시도 설정 등에 따라 이 한도는 모델 호출 횟수와 정확히 같지 않을 수 있다.
3. **결과 확인:** 반환된 `revised` 결과에만 **AI 제안 있음**을 표시한다. 해당 상세 화면은 원본을 먼저 보여주고, **AI 제안 보기 / 원본 보기**로 전환한다. 다른 레시피의 결과를 선택한 레시피에 대신 표시하지 않는다. 목록 밖의 레시피가 수정되면 그 원본 카드도 목록 뒤에 추가한다.
4. **거절과 오류:** `refused`, `failed`, `not_attempted`를 성공으로 바꾸지 않는다. 사용 한도·요청 제한·서버 AI 설정 문제는 안내하고 일반 목록과 원본은 유지한다. 실패 후 재요청은 사용자 조작으로만 한다.
5. **재열람·재요청:** 현재 앱 프로세스/동일 재고·사용자 조건에서 상세 제안은 재사용한다. 사용자 추가 요청으로 목록의 AI 버튼은 응답 후 다시 활성화되며, 다시 누르면 새 서버 요청을 보낸다. 기존 다른 요리의 제안은 유지하고 반환된 요리의 결과를 갱신한다. 앱 재시작 시 영구 보존하는 이력은 아니다. 재고·알레르기·조리도구 변경 시 이전 결과를 비우고 늦게 도착한 응답을 버린다. 현재 서버 API에는 알레르기·조리도구 필터가 없으며 화면에도 안내한다.

## 현재 서버 규격의 한계

- `/recipes/ingredient-catalog`, `/recipes/candidates`, `/recipes/{id}/revision`은 미공개 로컬 실험 경로이다. 기본 클라이언트는 이를 구현하거나 호출하지 않는다. 기존 실험 코드·테스트는 별도로 남겨 두었다.
- ID가 없는 수동 입력 재료를 임의로 무시하면 잘못된 AI 입력이 된다. 따라서 앱에 포함된 CSV의 정확한 ID/이름과 두 개의 명시적 별칭(달걀→계란, 후춧가루→후추)을 사용하며, 매핑하지 못하면 AI 요청만 차단한다. 일반 재료명 기반 목록은 계속 사용할 수 있다.
- 이 CSV는 현재 데이터의 스냅샷이다. 서버가 DB ID를 변경한다면 동적 ID 목록 API 또는 버전 계약이 필요하다. 이번 실제 batch 응답에 포함된 원본 재료들의 ID/이름은 CSV와 전부 일치했다. 응답 후 불일치 검사가 요청 전의 서버 ID 변경까지 예방해 주는 것은 아니다.
- batch API는 모든 조미료 가정의 레시피별 세부 정보까지 반환하지 않는다. 기존 목록 카드가 있으면 그 부족 재료·보유 상태를 유지한다. batch에서만 받은 원본에는 추측으로 ‘바로 만들 수 있음’을 표시하지 않는다. `revised`는 서버의 검증 결과로 표시하며 원본을 덮어쓰지 않는다.
- **서버 변경 없이 목록 + 서버 선택 AI 수정이 가능하다.** 사용자가 고른 특정 요리 하나만 수정하는 기존 구상을 실현하려면, recipe ID를 받는 서버 API가 필요하다. 이번에는 추가하지 않았다.

## 검증 증거

- 기본 클라이언트가 미공개 on-demand 경로를 요구하는 회귀 테스트를 먼저 실행해 실패를 확인했다.
- 원본 수량이 사라지는 문제를 AI 코드 리뷰와 새 회귀 테스트로 확인하고 수정했다. 사람이 직접 수정한 코드 사례로 기록하지 않는다.
- 최종 JVM **81개 통과**, 실패/오류/스킵 0. 냉장고 도메인·저장·삭제·추가순·조미료 체크·레시피 정렬·오래된 응답 방지와 새 batch 테스트를 포함한다.
- `lintDebug` 오류 0, 경고 30, hint 1. 테스트 코드의 잘못된 Compose 내부 ViewModel 생성은 린트 실패로 발견해 밖으로 옮겼다. 린트 억제나 baseline 추가는 하지 않았다.
- Cloud Test APK와 instrumentation APK 빌드 성공.
- 연결된 Galaxy S23 Ultra에서 **21개 UI 테스트 통과**. 기존 냉장고·정렬·삭제·기본 재료·자동완성 및 가짜 batch 제안→원본 전환, 실제 배포 서버의 일반 목록 표시를 확인했다. 실제 서버 목록 UI 테스트는 20개 레시피를 받았고 AI 요청을 하지 않았다.
- 실제 서버에 별도로 **단일 batch 요청, revision_limit=1**을 보냈다. 133개 후보 중 김치쌈밥(id 291)의 `revised` 결과와 수정 재료·단계를 받았다. 서버 내부 모델/키 설정이나 과금 내역 자체를 조회한 것은 아니다. 사진 인식 API 유료 검증은 이번에 실행하지 않았다.

## 직접 확인

휴대폰 또는 Android Studio Running Devices에서 **MyLittleChef Cloud Test**를 연다.

1. 냉장고 아이콘과 세 정렬을 확인한다. 관리/길게 누르기 삭제는 실제 데이터가 바뀌므로 삭제할 재료를 정하고 확인한다.
2. 내 정보에서 기본 재료 체크 화면을 열어 기존 선택을 확인한다.
3. 레시피 탭의 실제 서버 목록과 부족 재료 안내, 정렬을 확인한다.
4. 추가 AI 사용을 원할 때만 **AI 레시피 제안 받기**를 누른다. 결과 안내 후 **AI 제안 있음** 카드를 열어 원본/제안을 비교한다. 특정 요리 지정 요청은 현재 지원하지 않는다.

APK(로컬 ignored 산출물): `output/apk/MyLittleChef-iter3-cloudtest-server.apk`.
Android Studio 빌드 예: `./gradlew.bat :app:assembleCloudTest -PserverBaseUrl=http://158.101.141.165/`.
