# Iteration 3 — 냉장고 삭제·이미지·부족 재료 표시 개선

## 목표와 작업 기준

**11월 4일까지 완료**한다. 최신 `main`에서 로컬 브랜치 `frontend/iter3-inventory-and-images`를 만들고, 기능별로 구현·확인·커밋한다. 사용자가 로컬 결과를 확인한 뒤 **PR 하나**로 공유한다.

현재 GitHub의 Android 프로젝트 위치는 `android/`이다. 예전 작업 폴더의 미공개 기능을 통째로 가져오지 않고, 최신 코드에서 필요한 변경만 진행한다.

조리 완료 후 다 쓴 재료를 선택하는 기능은 **팀 논의 후 결정할 아이디어로 기록**한다. 이번 구현에는 냉장고 자체의 삭제 기능을 포함한다.

## 구현할 내용

**냉장고 재료 삭제**

- 재료를 길게 누르거나, 냉장고의 **‘관리’ 버튼**을 눌러 나타나는 재료별 삭제 버튼으로 삭제한다.
- 두 조작 모두 재료 이름을 보여주는 동일한 확인 창을 사용한다. 취소하면 재고가 유지된다.
- 삭제는 선택한 재료명에만 적용한다. 이미지가 같거나 분류가 같다는 이유로 다른 재료를 함께 삭제하지 않는다.
- 삭제 결과를 로컬 저장소에 반영하고, 저장에 실패하면 사용자에게 알린다.
- 레시피 탭으로 이동하면 변경된 재고로 자동 추천을 요청한다. 이전 요청의 늦은 응답이 최신 결과를 덮어쓰지 않도록 확인한다.

**부족한 재료 표시**

- 목록 카드에는 **‘부족한 재료 N개’와 최대 두 재료명**, 나머지는 ‘외 N개’로 요약한다.
- 상세 화면에서는 부족한 재료를 텍스트와 색상으로 구분한다. 색상만으로 의미를 전달하지 않는다.
- 서버가 반환한 부족 재료 정보를 우선 사용하고, 기본 조미료를 보유한 것으로 계산하는 현재 서버의 가정을 안내한다.
- 재고 변경 후 추천·즐겨찾기·상세의 안내가 서로 어긋나거나, 오래된 결과가 ‘바로 만들 수 있음’으로 남는 경우를 검증하고 수정한다.

**재료 아이콘과 레시피 사진**

- 기본 20종은 식재료 14종과 조미료 6종으로 한다. 여기에 기본 목록·물을 제외한 CSV 빈도 상위 재료 약 10종을 추가해 **총 30종을 우선 매핑**한다.
- 추가 후보는 다진마늘·후추·깨소금·다진파·홍고추·청고추·식초·고추장·무·실파다. 다진마늘과 마늘처럼 관련된 항목은 아이콘을 공유할 수 있지만 재고 데이터는 구분한다.
- 우선 재료는 개별 아이콘을 사용하고, 나머지는 채소·고기·해산물·알/두부·곡류·조미료 등의 분류 아이콘 또는 일반 대체 아이콘을 표시한다.
- 레시피 사진은 자취 요리에 적합하고 정확한 사진을 확보할 수 있는 **20개를 선정**한다. 레시피 ID로 연결하고 목록과 상세에 같은 사진을 사용한다. 미확보 항목에는 일반 요리 대체 이미지를 표시한다.
- 아이콘은 [Noto Emoji 자산](https://github.com/googlefonts/noto-emoji/blob/main/svg/LICENSE)을 우선 검토한다. 사진은 [Wikimedia Commons의 개별 파일 조건](https://commons.wikimedia.org/wiki/Commons:Reusing_content_outside_Wikimedia/en)을 확인해 선택한다.
- 이미지 파일은 앱에 포함한다. 출처·제작자·라이선스·수정 내역을 기록하고 앱에서도 출처를 확인할 수 있게 한다. 기존 추천 API와 서버 배포 설정을 유지한다.

## 검증과 코드 이해

- 삭제 확인·취소·마지막 재료 삭제·연속 삭제·재실행 후 유지 여부를 검사한다.
- 두부·계란처럼 재고에 따라 추천이 달라지는 재료로 삭제 전후 요청과 결과를 확인한다. 기본 조미료 삭제는 현재 서버 정책과 구분한다.
- 부족 재료 0개·1개·여러 개, 긴 이름, 아이콘 없는 재료, 사진 없는 레시피를 확인한다.
- 변경에 필요한 단위 테스트와 Android UI 테스트를 추가하고 기존 테스트·린트·빌드를 실행한다. 자동 검증은 로컬 Mock 서버를 기본으로 한다.
- 휴대폰 검증에는 분리된 `.cloudtest` 앱을 사용한다.

각 기능을 보여줄 때 내가 **변경 파일, 주요 함수, 데이터 흐름, 검증할 상황**을 한국어로 설명한다. 사용자는 핵심 코드를 읽고 예상 결과를 적어본 뒤 앱 결과와 비교한다. 직접 수정할 필요가 생기면 작은 부분부터 함께 확인하며 진행한다.
