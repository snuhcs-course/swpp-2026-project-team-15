# Iteration 1 AI 사용 기록 — 권혁준 (PM)

**도구:** Codex 대화 및 프레젠테이션 제작 도구. 당시 개별 대화의 정확한 모델 표기는 확인 필요.  
**범위:** PM 인수인계, TA 발표 준비, 문서의 Mermaid 시각화 및 제출 문서 Markdown 작성 보조. 아래는 담당 작업과 실제 산출물 중심의 기록이다.

## 1. AI를 사용한 곳과 사용하지 않은 곳

- **PM 인수인계:** PM 교체 시 확인할 일정표, 브랜치, Wiki, TA 피드백, 미결정 사항을 정리하는 초안과 문서 구조에 Codex를 사용했다. 최종 산출물은 [`docs/pm-handoff.md`](https://github.com/snuhcs-course/swpp-2026-project-team-15/blob/main/docs/pm-handoff.md), [PR #1](https://github.com/snuhcs-course/swpp-2026-project-team-15/pull/1)이다. 실제 일정·담당자·의사결정의 출처는 팀 논의와 일정표다.
- **발표 준비:** TA 미팅용 영어 슬라이드 초안, 구성, 한국어 대본 및 예상 질문을 만드는 데 AI를 사용했다. 기술 선택을 확정된 것처럼 말하지 않도록 표현을 여러 번 수정했다. 최종 PPT의 선택·편집은 PM이 했다. 로컬 발표 파일: `output/presentations/My_Little_Chef_TA_Meeting_Green_Design_Final.pptx`.
- **시각화:** ReqSpec의 사용자 흐름과 Design의 현재/제안 아키텍처 및 ER 관계를 Mermaid 코드로 나타내는 데 AI를 사용했다. [PR #2의 영문 문서](https://github.com/snuhcs-course/swpp-2026-project-team-15/pull/2)에 Mermaid 원문이 있다. PM은 도표가 실제 구현과 제안을 혼동하지 않도록 검토하고, Word/PDF 삽입용 캡처는 직접 처리하기로 했다.
- **제출 문서 작성 보조:** 10월 9일 ReqSpec·Design Markdown의 문장 구성과 영문·국문 정리에 Codex가 실제로 관여했다. 기능 범위·날짜·구현 여부에 관한 최종 판단은 팀과 PM의 몫이다. 이 항목은 일정표의 별도 구현 작업과 구별한다.
- **AI 미사용:** 기존 `P` 작업의 책임 배분, 추가 `A` 작업의 생성, 일정표의 완료 범위와 시간 확정은 팀원들과 직접 논의해 PM이 결정했다. 일정표의 작업별 `AGENT HOURS`를 PM 개인의 AI 사용량으로 해석하지 않는다. 서버·Android·레시피 DB 코드도 PM이 AI로 작성했다고 주장하지 않는다.

## 2. 실제 프롬프트 발췌

아래 인용은 문장 자체를 고치지 않은 발췌다. 대화 내 개별 전송 날짜는 별도로 확인되지 않아 임의의 날짜를 붙이지 않았다.

> 내 생각에 너랑 내가 좀 더 git 리포지토리에 문서나 위키같은 거를 좀 수정 보완하고 그 다음에 저런 문서를 작성해야 할 거 같음. 일단 팀원들간의 회의 기록 같은 것도 업로드를 좀 해야 하고, 그 외에도 좀 이후에 다른 PM도 관리하기 위해 세팅해둬야 할 거 같아서 이 부분부터 진행하고, 그 뒤에 문서들을 완성해보자

> 제안 부분 없애고, 미확정 부분은 여러 가지를 고려하고 있다, 이런 식으로 표현하면 될 거 같아.

> 다음 md 내용을 시각화해서 mermaid로 표현해줘

이 마지막 문장은 PM이 10월 9일 사용한 프롬프트 문구로 제공했다.

## 3. 잘된 점

- PM 인수인계 문서가 [커밋 `80fec41`](https://github.com/snuhcs-course/swpp-2026-project-team-15/commit/80fec41)에 포함되어 다음 PM이 확인할 파일, 결정 로그, 미완료 항목을 한곳에서 찾을 수 있게 됐다. 절약 시간은 측정하지 않았다.
- 발표 자료에서 백엔드, 재고 저장, 인식 방식의 장단점을 비교하고, 결정되지 않은 선택을 후보로 표현하도록 수정하는 데 도움이 됐다.
- Mermaid 도표는 앱 목업, 별도 SQLite DB, 미래 서버 연동 사이의 경계를 짧게 보여줬다. 실제 구현 여부는 도표만으로 판단하지 않고 코드와 브랜치 상태를 확인했다.

## 4. 오류·부정확한 가정

- Codex가 처음 만든 ReqSpec·Design 개정 이력은 세 버전을 모두 10월 9일 작성으로 적었다. Git 업로드 날짜를 개인 작업의 시작 날짜로 잘못 가정한 것이다. PM이 기존 작성 시점을 알려주어 0.1은 9월 30일, 0.2는 10월 7일, 0.3은 10월 9일로 바로잡았다([수정 커밋 `9eff8d1`](https://github.com/snuhcs-course/swpp-2026-project-team-15/commit/9eff8d1)). 추가 확인과 문서 수정 시간이 들었으나 정확한 분 단위는 기록하지 않았다.
- 발표 초안에서 미확정 기술 선택이나 제안 기능을 단정적으로 읽을 위험이 있었다. PM이 문구를 다시 요청하고 최종 슬라이드를 직접 확인했다.

## 5. 프롬프트 수정 사례

- **이전:** “백엔드를 둘 중에 어떤 걸로 하는게 좋을까? 그리고 냉장고 재고도 서버나 기기에 두는 것에 대해서 너가 한 번 판단을 해서 장단을 알려주면 내가 선택을 해볼게.”
- **이후:** “제안 부분 없애고, 미확정 부분은 여러 가지를 고려하고 있다, 이런 식으로 표현하면 될 거 같아.”
- **효과:** 기술 비교 자체는 유지하면서, 팀이 아직 확정하지 않은 선택을 발표에서 확정안처럼 보이지 않게 했다. 위 두 문장은 각각 실제 프롬프트에서 인용했다.

## 6. 사람이 직접 고친 것과 이유

- PM은 일정표의 작업·담당자·추가 `A` 작업을 팀원들과 결정했다. AI의 추천을 일정표 결정의 출처로 삼지 않았다.
- 발표용 PPT의 최종 내용과 길이, 미확정 사항의 표현을 직접 판단했다. AI가 팀 합의나 구현 상태를 대신 확인할 수 없기 때문이다.
- Mermaid를 PDF용 그림으로 자동 변환하지 않고, 렌더링을 눈으로 확인한 뒤 PM이 캡처해 Word에 넣기로 했다.

## 7. 다음 Iteration에 적용할 점

AI가 문서나 발표의 구조를 빠르게 제시해도 작업 날짜, 팀 합의, 구현 상태는 원자료와 담당자에게 확인한다. PM의 AI 사용 기록과 팀원의 AI 사용 기록을 작업별로 분리한다.

**보고서 편집 메모:** 제출 전 정확한 Codex 모델 표기와 최종 PPT 파일명을 PM이 확인한다. 이 메모는 PDF 본문에 포함하지 않는다.
