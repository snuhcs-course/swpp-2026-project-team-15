# Revision LLM Judge 파일럿 실험 보고서

아래 수치와 raw 결과는 최초 실행 기준을 그대로 유지한다.

## 1. 요약

저장된 레시피 5건에 대한 Gemini Judge 평가를 사용자 독립 채점과 비교했다.
숫자 점수가 있는 21개 항목 중 17개가 일치했다(81.0%). N/A까지 포함하면
25개 항목 중 21개가 일치했다(84.0%). 사례 전체가 일치한 것은 2/5건이다.

5건 모두 출력 검증을 통과했지만, 이것이 채점 타당성을 뜻하지는 않는다.
R02a에서는 한국어 표현을 과도하게 해석해 감점했고, R01b에서는 명시된
재료 보유 정보를 무시해 적절한 거절을 오답 처리했다. R10c의 방법 적절성은
사람도 불확실성을 명시한 항목이므로, 불일치를 곧 Judge 오답으로 단정하지 않는다.

## 2. 목적과 실행 조건

- 목적: 출력 형식뿐 아니라 A–E rubric의 실제 판정과 사람 채점의 일치 여부를 점검한다.
- 실행일: 2026-11-22. 순서: **R02a → R01b → R01c → R10c → R04c**.
- 코드 기준: `d596d86`. 공유 Judge의 검증·payload 구성 로직을 로컬 Gemini 도구에서 재사용했다.
- 레시피 생성: 기존 OpenRouter runner, 기본 모델 `google/gemini-2.5-flash-lite`.
  R02a는 이전 실행의 저장본을 재사용했고, 나머지 네 사례는 새로 실행했다.
- Judge: Gemini 직접 API, `gemini-3.5-flash-lite`, temperature 0, 최대 출력 1,800토큰,
  사례당 1회, HTTP 재시도 없음.
- rubric: `revision-evaluation-a-e/2026-11-19`; 결과 형식: `revision-evaluation-judgment/v2`.
  정확한 prompt hash와 원본 observation hash는 각 `judgment.json`에 보존했다.
- 입력: 먼저 runner 결과를 파일로 저장한 뒤, 복사한 `observation.json`에서
  보유 재료·기본 양념·원본 레시피·최종 수정 또는 거절 응답만 추려 Judge에 전달했다.
  사람 점수와 case의 기대 결과는 Judge에게 제공하지 않았다.
- 사람 평가: 사용자가 독립 채점 결과로 제공한 1인 평가를 그대로 기록했다.
  결과 제공 시점은 Judge 실행 후이며, 사전 등록·블라인드 평가 여부는 확인하지 않았다.
  따라서 아래 지표는 확정 정답 대비 정확도가 아니라 **사용자 채점과의 일치도**다.

## 4. 사례별 해석

### R02a — C·D의 불필요한 감점

- 사람: 전 항목 2점, 별도 지적 없음. Judge: C=1, D=1.
- 저장된 수정본은 당근을 삭제하고 대파를 유지했다. 1단계는 “대파를 잘게 다진다”,
  2단계는 “계란을 풀고 소금과 다진 채소를 섞는다”다.
- Judge는 ‘채소’를 복수 vegetables로 해석해, 대파만 남았으므로 2단계도 고쳐야 한다고 판단했다.
  `required_adjustments`에도 이 요구를 추가한 뒤 C를 감점했고 같은 표현으로 D도 감점했다.
- 사용자 평가와 입력 문맥을 기준으로 보면, 해당 표현만으로 모순이나 미반영 조정을
  확정할 근거가 부족하다. 근거 없는 필수 조정 생성과 한국어 해석 문제의 후보 사례다.
  같은 근거가 두 축에 사용됐다는 사실만으로 중복 감점 금지 규칙을 새로 가정하지는 않는다.

### R01b — 명시된 unavailable을 무시한 거절 오판

- 사람: A=2, “잘 거절함”. Judge: A=0. B–E의 N/A는 일치했다.
- 입력의 밥은 `availability: unavailable`이며, inventory와 effective_staples에도 없다.
  최종 응답은 “요리 이름에 들어간 밥이 없어서 이 요리로 바꾸기 어려워요.”다.
- Judge는 원본 레시피에 밥이 있다는 점과 기본 재료를 가정할 수 있다는 추론으로
  거절을 부적절하다고 판정했다. 원본에 필요한 재료와 실제 사용 가능한 재료를 혼동한 것이다.
- 이 정보는 경량 payload에도 이미 있으므로, 관찰된 오판을 입력 정보 손실 탓으로
  돌릴 근거는 없다. 이번 비교에서 점수 차이가 가장 큰 항목이다(2점).

### R01c — 사람·Judge 전 항목 일치

- 양쪽 모두 전 항목 2점이며, 사용자 별도 지적은 없다.
- 대파·계란을 생략한 수정본이다. 쪽파를 사용하지 않았다는 이유로 감점하지 않았다.
- 실행 직후 에이전트가 2단계의 목적어 없는 “볶는다”를 검토 후보로 언급했으나,
  이는 사용자 채점과 별개인 사전 관찰이다. 본 보고서는 사용자 D=2를 임의로 변경하지 않는다.

### R10c — 방법 적절성의 불확실한 불일치

- 사람: B=1, 나머지 2점. Judge: 전 항목 2점.
- 사용자는 부침가루 없이 감자전으로 볼 수 있는지, 단순 감자·양파구이에 가까운지
  확신하지 못했으며, 감자를 곱게 갈면 가능할 것 같다는 의견도 함께 제공했다.
- 저장본은 실제로 감자와 양파를 곱게 갈고, 물기를 약간 따라낸 뒤 소금을 섞어
  얇게 굽도록 한다. 이 관찰만으로 B=1 또는 2를 확정하지 않는다.
- **사용자가 불확실성을 명시한 참고 점수**로 B=1을 유지해 일치도에 포함했다.
  전문가 검토 또는 근거 확인 전에는 Judge의 확정 오답 사례로 사용하지 않는다.
  평가자 불확실성을 모델의 `deferred` 상태로 소급 변환하지도 않는다.
- runner의 최초 응답은 `unavailable_ingredient` 검사에 실패했고, 재요청으로 얻은
  최종 수정본을 Judge가 평가했다. 첫 응답과 최종 응답을 혼합해 평가하지 않았다.

### R04c — 남은 tips 불일치 감점에 일치

- 양쪽 모두 D=1, 나머지 2점이다.
- 돼지고기를 참치캔으로 바꿨지만 tips에는 “고기는 속까지 완전히 익혀 먹는다”가 남았다.
  사용자와 Judge 모두 이 국소적인 불일치를 지적했다.
- tips를 경량 입력에 유지한 것이 이 사례의 문제 발견에 필요한 정보를 보존했다.
  다만 한 사례만으로 입력 압축 전반의 정보 보존성을 입증한 것은 아니다.

## 5. 결론과 다음 검증

현 상태는 **API 연결·저장·출력 검증은 통과했으나, 자동 채점 신뢰성은 추가 보정이 필요**하다.
우선 검토할 것은 입력 확대보다 이미 제공된 보유 상태 준수와 근거 없는 필수 조정 생성 억제다.

1. inventory / effective_staples / availability의 의미와 원본 레시피의 차이를
   프롬프트에서 더 명확히 할지 검토한다. 없는 재료를 임의로 가정하지 않도록 한다.
2. C의 필수 조정은 실제 기능·분량·손질·순서 변화에 근거하도록 하고, 단순 표현 취향이나
   근거 없는 단복수 해석으로 조정을 만들어내지 않는지 확인한다.
3. R10c는 방법의 역할·물성 충족 여부를 사람이 먼저 재검토한다. 불확실한 채점을 맞추기 위해
   Judge를 변경하지 않는다.
4. 변경 후 동일 저장본으로 재평가하되 새 결과 디렉터리와 새 prompt hash를 사용한다.
   이후 별도 사례와 반복 평가로 일반화·안정성을 검증한다.

이 보고서 작성에서는 추가 API 호출, 코드·rubric 수정, 재채점 또는 커밋을 하지 않았다.

## 6. 보관 자료와 한계

- [사람 채점 원문](human-evaluation.md). Judge 점수와 실행 조건은 위 표와 본문에 기록했다.
- 원본 JSON 자료는 로컬 `output/judge-five-20261122T120649324034Z/`에 보관하며,
  이 커밋용 보고서 묶음에는 포함하지 않는다.
- 각 사례 폴더: `observation.json`, `source.json`, `original-recipe.json`,
  `service-response.json`, `judge-input.json`, `judge-raw.json`, `judgment.json`.
- 위 로컬 디렉터리의 R02a/R01c/R10c/R04c 하위 폴더에 `revised-recipe.json`이 있다.
  R01b는 `service-response.json`의 거절 응답만 있고 수정 레시피는 없다.
- 추가 runner HTTP는 총 4회(R01b=0, R01c=1, R10c=2, R04c=1), Judge HTTP는 5회다.
  R02a의 과거 생성 비용은 이 추가 호출 수에 포함하지 않았다.
- Judge 토큰·비용·지연시간은 이 실행에서 계측하지 않았다. 미측정은 0이 아니다.
- 5개 수동 선택 사례, 1인 비전문가 평가, 모델당 사례별 1회 호출이다.
  사람 채점 숫자 21개 중 19개가 2점이고, 0점 기준 사례와 deferred 사례가 없다.
  따라서 전체 rubric 경계나 반복 일관성 검증은 아직 충족하지 못했다.
- 사람 점수는 사용자 독립 평가로 수집됐지만 사전 등록된 정답 세트가 아니며,
  이 사례로 프롬프트를 조정하면 이후 동일 사례의 개선은 보정 결과이지 독립 검증이 아니다.
