# 프롬프트 최소 보정 후 동일 저장본 재평가

## 결론

**이번 보정은 채택 가능한 개선을 입증하지 못했다.** 목표였던 R02a·R01b의 오판이
그대로 남았고, R01c에 새 감점이 생겼으며 R10c는 로컬 계약 위반으로 reject됐다.
실험 직후 프롬프트 수정은 미커밋 후보 상태로 남겼으며, 이후 사용자가 revert하기로 결정했다.
이 문서는 미채택 실험의 기록이다. 사용자 점수나 rubric을 결과에 맞춰 바꾸지 않았다.

## 조건과 변경 범위

- 기준 실험: [독립 채점 비교 보고서](judge-human.md).
- 기존과 같은 Gemini `gemini-3.5-flash-lite`, temperature 0, 최대 출력 1,800토큰.
- R02a → R01b → R01c → R10c → R04c 순서, 각 1회(추가 Judge HTTP 5회).
  자동 재시도나 레시피 재생성은 없었다. 원본 저장 observation과 minimized payload가
  기존 실험과 동일한지 실행 중 확인했다. 사람 점수는 모델 입력에 포함하지 않았다.
- 공유 변경은 system prompt 5줄 추가와, 기존 mock HTTP 테스트에서 그 문구의
  실제 요청 전달을 확인하는 assertion 4줄뿐이다. payload/schema/점수 경계는 그대로다.
- 추가 지침: 보유 상태는 inventory·effective_staples·availability를 기준으로 삼고,
  원본 레시피에 있다는 이유로 보유를 가정하거나 기본 재료를 추가하지 않는다.
  필수 조정·감점은 실질적 조리/일관성 근거가 필요하며, 한국어 명사의 단복수나
  문맥상 참조가 명확한 일반 표현을 근거 없이 문제 삼지 않는다.
- prompt/schema hash: 기존 `298587f2ac8c12b20b48548ff067565f8145e3551c5c77c1c1482dd632d22ca3`
  → 신규 `b70210efb53a01a12e9d51b8d3107b6fcc75d613943b673a6330c8ac5fb8efd2`.
  [프롬프트 변경 diff](prompt-change.diff)를 함께 보관한다. 기준 프롬프트/schema는
  코드 `d596d86`의 `judge.py`이며 schema는 변경하지 않았다.
  전체 신규 system prompt/schema의 로컬 보관 위치는
  `output/judge-recheck-20261122T123737987712Z/prompt.json`이다.

## 점수 비교

각 점수열은 A/B/C/D/E 순서다. 원점수나 reject를 자동 보정하지 않았다.

| 사례 | 사용자        | 기존 Judge    | 보정 후 Judge                |
| ---- | ------------- | ------------- | ---------------------------- |
| R02a | 2/2/2/2/2     | 2/2/1/1/2     | 2/2/1/1/2                    |
| R01b | 2/NA/NA/NA/NA | 0/NA/NA/NA/NA | 0/NA/NA/NA/NA                |
| R01c | 2/2/2/2/2     | 2/2/2/2/2     | 2/2/2/1/2                    |
| R10c | 2/1/2/2/2     | 2/2/2/2/2     | **reject**（raw: 2/1/1/2/2） |
| R04c | 2/2/2/1/2     | 2/2/2/1/2     | 2/2/2/1/2                    |

- 출력 검증 통과: 기존 5/5 → 보정 후 4/5.
- 전체 사례의 완전 일치: 기존 2/5 → 보정 후 1/5(R04c).
  reject된 R10c를 일치 사례로 포함하지 않았다.
- 두 실행 모두 검증을 통과한 동일 4개 사례만 비교하면 숫자 일치는
  기존 13/16(81.3%) → 보정 후 12/16(75.0%). 이는 R10c를 제외한 조건부 비교다.
  전체 5개 기준 기존 17/21(81.0%)과 보정 후 부분집합 비율을 직접 비교하면 안 된다.
- R10c의 raw B=1이 사용자 점수와 같아졌어도 **거절된 응답의 일부**이므로
  유효한 일치율 개선으로 집계하지 않았다.

## 관찰과 실패 원인

### R02a: 단복수 오판 지속

보정 후에도 “다진 채소”가 복수이므로 대파만 남은 상황과 맞지 않는다는 이유로 C/D를 감점했다.
명시적 지침 추가만으로 이 추론을 억제하지 못했다. 관찰 결과만으로 모델 일반의
한국어 이해 성능이나 프롬프트의 인과 효과를 확정하지 않는다.

### R01b: 입력에 없는 기본 재료 가정 지속

신규 reason은 밥을 “universal staple and available in the context”라고 했다.
입력에서는 밥이 unavailable이고 effective_staples에도 없으므로, 여전히 제공된
제약보다 일반적 가정을 우선한 판정이다. 기존 최종 거절 응답은 바꾸지 않았다.

### R01c: 새 D 감점

대파가 사라진 뒤 목적어 없이 남은 “팬에 식용유를 두르고 볶는다”를 D=1 근거로 삼았다.
사용자는 D=2로 채점했으므로 일치도는 낮아졌다. 이 사유는 사람과 논의할 수 있는
국소적 해석 차이이며, 사용자의 확정 승인 없이 정답 점수를 바꾸지 않는다.

### R10c: 단일 조정에 C=1을 반환해 reject

raw 응답에는 required_adjustments가 “부침가루 생략에 따른 수분 조절 또는 전분 활용”
하나인데 C=1이다. 기존 계약상 단일 조정은 C=0 또는 2만 허용하므로
`one required adjustment permits only score 0 or 2` 규칙에 걸린다.
이는 새 검증 규칙이 아니라 원래 있던 계약의 정상 작동이다.
검증을 완화하거나 raw 점수를 고쳐 통과시키지 않았다.

### R04c: 기존 일치 유지

고기를 완전히 익히라는 tips가 남은 점을 D=1로 평가해 사용자와 일치했다.

## 검증과 다음 판단

- 오프라인 테스트 62개 통과(기존 Starlette deprecation warning 1건), server 설정 Ruff,
  OpenSpec strict, diff whitespace 검사 통과. Mock 검증은 프롬프트 전달만 보장하며
  실제 의미 판정의 회귀 방지를 보장하지 않는다.
- 이 5개는 이미 문제 발견·프롬프트 보정에 사용한 사례이므로 독립 holdout이 아니다.
  모델별 반복 호출도 없어 출력 변동과 프롬프트 효과를 분리할 수 없다.
- 다음 후보는 규칙을 단순 덧붙이기보다 system prompt에서 입력 제약과 감점 근거의
  우선순위를 명확히 재구성하는 것이다. 필요하면 짧은 대조 예시도 별도 실험하되,
  정답 점수나 사례 ID를 주입해 맞추지는 않는다. 모델 비교도 별도 선택지다.
- 이 미채택 후보는 사용자 결정에 따라 revert 대상이며, 결과를 숨기기 위한
  자동 반복 호출이나 커밋/푸시는 하지 않았다.
- 원본 JSON 자료는 로컬 `output/judge-recheck-20261122T123737987712Z/`에 보관하며,
  이 커밋용 보고서 묶음에는 포함하지 않는다. 각 사례의 source.json, judge-input.json,
  judge-raw.json과 유효한 judgment.json을
  보관했다. R10c에는 judgment.json 대신 judge-error.json이 있다.
  Judge 토큰·비용·지연시간은 미측정이며 0으로 간주하지 않는다.
